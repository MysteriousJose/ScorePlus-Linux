## 1. Branch and version model

Three refs with three different jobs. This is the part that has been failing.

| Ref | Job | Rules |
| --- | --- | --- |
| `upstream` + tag `b1.1` | The Windows reference. | Read-only. **Never** built here, **never** merged wholesale into a Linux branch. Consulted file-by-file. |
| `linux` | The shipped Linux build (a1.4L). | **Frozen.** Only ever fast-forwarded from `linux-dev` at release time. No feature commits, no merges, no experiments. |
| `linux-dev` | Integration for the next build (a1.5L). | All porting happens here. Always compiles. Feature work lands via short-lived branches into it. Never tagged. |

Promotion is one directional and happens only on a confirmed build:

```
feature branch ──PR──▶ linux-dev ──(gate passes)──▶ tag a1.5L ──ff-only──▶ linux ──▶ release workflow
```

`linux` is never the place work happens, so "don't touch linux except for confirmed builds" becomes mechanically enforced instead of remembered.

**Setup (phase 0):**

```bash
git branch linux-dev linux          # absent today; linux-dev is a fresh clone of the release
git push -u origin linux-dev
# protect `linux` on GitHub: require PR + green CI, forbid direct pushes
git tag upstream-b1.1 17fc7a3       # durable local pin of the Windows reference
```

**One thing to confirm before starting:** `linux` is one commit *past* tag `a1.4L` (`fb2fd23 "add appimage support"` vs `de0405b`). Decide whether a1.4L means the tagged commit (and the appimage commit is unreleased) or the branch tip. The plan assumes `linux-dev` branches from `fb2fd23`, the tip, so nothing unreleased is lost.

**Tag collision, already live.** `.github/workflows/release-linux.yml` triggers on `tags: ['a*', 'b*', 'v*']`, and its own comment calls `b1.0` a public release label. Upstream uses `b*` for Windows builds — and tag `b1.1` now exists in this repo (it was fetched from upstream). Pushing tags as-is can build and publish a *Linux* release from a *Windows* commit. The existing `a1.4L` already shows the right convention: Linux releases are `a<ver>L`. Narrow the trigger to that shape and drop `b*`:

```yaml
tags: ['a*L', 'v*']
```

## 3. Ordering insight

b1.1's headline features are **video and camera features** — replay booth, camera wall, multiview, score-value videos, keyed celebrations. The Linux build's video stack is 1,613 lines of inert stand-ins:

- `BitmapSource.Create` returns a 1×1 placeholder, `Draw` is empty → every bitmap is blank.
- `VideoCapture.IsOpened()` returns `false` → no camera, no replay, no multiview.
- `WasapiOut` / `MMDeviceEnumerator` are no-ops → no routed audio, no meter, no horn.
- `MediaElement` holds a position and never decodes → cues "play" and show nothing.

So the port is not ordered by feature size, it is ordered by the media backend. Two tracks run in parallel: **Track B** (no media dependency, unblocked today) and **Track A** (the backends that unlock the rest).

## 4. Phases

Estimates assume one developer who knows this codebase.

### Phase 0 — Make the model real (0.5–1 day)

- `git branch linux-dev linux`, push it, protect `linux` (PR + green CI, no direct pushes).

### Phase 1 — Core to b1.1, verbatim (2–3 days)

### Phase 2 — Track B: b1.1 features with no media dependency (1–2 weeks)

### Phase 3 — Track A: replace the shims with real backends (2–3 weeks)

Delete each shim only as its real backend lands; the exit criterion is `grep -r "WpfCompat\|PortTypeAliases\|OpenCvSharpCompat" src/` returning nothing.

| Step | Replaces | Behaviour |
| --- | --- | --- |
| `MediaProbe` | — | Locate `ffmpeg`/`ffprobe`/`paplay`/`pactl`/`v4l2-ctl`/`xrandr`/`fc-list`; missing binary = explicit, visible status, app stays usable. |
| `LinuxVideoPlayer` | `MediaElement`, `BitmapSource`, `RenderTargetBitmap` | `ffmpeg -ss … -re -i … -f rawvideo` into a persistent `WriteableBitmap` behind an `Image`; `VideoSurface`'s cue/seek/loop logic stays as-is. |
| `LinuxAudioEngine` | `WasapiOut`, `MMDeviceEnumerator`, `AudioFileReader` | `ffmpeg -af volume= | paplay -p <sink>`; `pactl list sinks` for devices; position timer for the waveform/meter; un-stubs horn, speaker routing, audio cues. |
| `LinuxCameraEngine` | `VideoCapture`, `Mat`, `VideoWriter` | `ffmpeg -f v4l2` frames, MJPEG segment recording, concat export; keeps the existing 6-segment prune and `AppPaths` layout. |
| `LinuxDisplays` | `ScreenFit`, `WindowFullscreen` Win32 | `xrandr` → `RenderScaling` division, `Screens` fallback. |
| `Fonts` / `Theme` / dialogs / updates | WPF paths | `fc-list`; GTK `settings.ini`; `StorageProvider`; tar.gz + `install.sh` handoff. |

Gate: behaviours, not "no exception" — a cue renders frames; a paused scrub shows the right frame; loop rewinds; an audio cue is audible on a named sink at the slider's level; a webcam shows live frames; a replay export is playable. CI runs generated ffmpeg fixtures for video; camera and audio stay documented manual smoke items.

### Phase 4 — Media-dependent b1.1 features (2–3 weeks)

`ReplayBooth` (1,145) → `CameraWallPage` (269) → `MultiviewWindow` + `MultiviewLayout` (1,264) → horn + speaker routing + meter (410) → then the `ScorebugRender` growth (score-value videos, keyed celebrations, logo finishes) and the `ScorebugEditorWindow` +620 in editing UI.

Gate: multiview shows live cameras; the replay booth stages and switches within b1.1's timing rules; celebration videos play keyed over the scorebug.

### Phase 5 — Reclaim the reduced windows (3–5 weeks)

For each file in section 2c, diff `b1.1` → `linux` and classify **every** hunk: (a) platform swap — keep; (b) lost feature — restore; (c) dead code — drop, with the reason written down. The classification is the deliverable that stops the next merge from repeating the loss.

Order by size of loss: `MotionMakerWindow` −2,033 → `MediaSession` −938 → `ScorebugCanvasView` −907 → `MotionPlayback` −347 → `VideoSurface`/`Media` (−578) → `RemotePage`/`RemoteControl` (−529; the remote console is a live operator dependency, check it explicitly) → `Theme` −240 → `ColorPickerWindow`, `Keybinds`, `Stepper`, `PaintTextureWindow` tails.

Gate: no hunk left unclassified; nothing still marked `lost`.

### Phase 6 — Tests and promotion (1 week)

- Restore UiSmoke toward b1.1's 6,313 assertions (from 1,138) as features land, not in one heroic push.
- CI on `linux-dev`: ledger job, three suites, AppImage + `.deb` build, install smoke on a clean VM.
- Then the promotion procedure below.

Total: roughly **9–13 weeks** of focused work; phases 3 and 5 dominate.

## 5. Promotion: how `linux` actually gets updated

Only on a confirmed build, in this order:

1. `linux-dev` green: builds, all three suites pass, AppImage and `.deb` produced.
2. Install both artefacts on a clean machine and run the smoke list: video cue, seek, loop, audio to a named sink, camera, replay export, remote console from a phone, scorebug edit + render, league cloud with no network.
3. Ledger check: nothing `outstanding` inside this release's scope; everything else explicitly `deferred` with a reason.
4. `git tag -a a1.5L -m "..."` on `linux-dev`'s tip.
5. `git checkout linux && git merge --ff-only a1.5L && git push` → the release workflow publishes.
6. Hotfix path: fix on `linux-dev`, tag `a1.5L.1`, fast-forward `linux` again. Never commit on `linux`.

Version numbering note: tags `a1.7`, `a1.51`, `a1.60` also exist and sort *above* `a1.4L`, so the Linux line's numbering is already ambiguous. Next release should be `a1.5L` and the old `a*` tags should be treated as historical, not as a sequence to continue.

## 7. Risks

| Risk | Why it is real | Mitigation |
| --- | --- | --- |
| A merge silently drops the upstream side — again. | Happened at `8611097` and at PR #9 (`50f9682`), both leaving the Linux tree untouched. | Ledger CI job; per-feature PRs; never merge `b1.1` wholesale; when a tree-level conflict appears, "ours" is never the resolution without a written reason. |
| Shims keep the build green while the product is dead. | 1,613 lines of inert stand-ins, 56 stub markers. | Phase 3's exit is zero shim references; tests assert visible media behaviour. |
| Restoring Core breaks the app, tempting a third de-featuring. | Core drift is where the 4.5k lines went. | Fix Desktop; any Core deviation needs an `excluded` row with a reason. |
| Windows-only tags trigger Linux releases. | `release-linux.yml` fires on `b*`; tag `b1.1` is now present locally. | `tags: ['a*L', 'v*']`. |
| `upstream/main` keeps moving past `b1.1`. | Already at `963c15b` ("Update index.html"). | Pin `upstream-b1.1`; port from the tag, never from `main`. |
| The 13 renamed `*.xaml(.cs)` surfaces inflate the "missing file" count. | They are converted, not lost. | Classify renames from real gaps before estimating (done in 2b vs 2c). |
| Long phases on a single-dev branch. | `linux-dev` drifting from `linux` for months. | Release in slices: a1.5L can ship Track B alone; a1.6L takes the media features. |
| No camera or audio sink on CI. | Verifiability. | ffmpeg-generated video fixtures in CI; camera/audio on the documented manual smoke list. |
